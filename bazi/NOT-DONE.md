# 三项未复刻的探索结论

> 2026-11-12 · 每项都有可复现的探针脚本

## 一、起运秒位 —— 已到方法上限（不是能力不足）

### 新做的验证（前四次修法都没做过）

**直接反解 δ**：把 API 输出当作「要求的节气时刻」反推，得到每个样本隐式要求的 δ：

```
δ_required = (名义秒_API + bias) / 120 − 距节真实秒      （顺行）
δ_required = 距节真实秒 − (名义秒_API + bias) / 120      （逆行）
```

**结果**：按 `(年, 节气)` 分组后，**组内 δ 标准差中位仅 0.06 秒，最大 0.37 秒**
（整体误差是 1.53 秒）。

这个 0.06 秒正好等于斜率漂移量：`K ≈ −0.0028 s/天 × 15 天 ≈ 0.042 s`。

**含义**：模型 `名义秒 = round(距节真实秒 × 120) − bias` **是正确的**，
瓶颈纯粹是 δ 表标定精度，而且已经接近可达到的下限。

### 决定性验证：重新推导得到同一张表

用「节气名级中位 + 年份残差收缩」两层估计重新拟合 δ，
再做**留一年交叉验证**（140 个年份，逐年前推）：

```
留一年交叉验证: 3145/7651 = 41.11%
逐位: 年 100.0%  月 99.3%  日 98.7%  时 97.7%  分 86.7%  秒 46.3%
```

**与现有实现逐位完全一致。** 换成中位数、均值、众数、加全局斜率四种估计方法，
结果都在 5%–13% 之间（更差），说明现有表已是该方法族的最优解。

**结论**：独立方法重新推导出同一结果 —— 现有实现已到上限。

探针：`probe_delta_solve.py`（反解 δ 散布）、`probe_delta_layer.py`（留一年 CV）

### 第二轮：结构分析（更细的证据）

建立缓存后（`cache_qiyun.py`，7651 条，含 `tss` 引擎实测值与浮点 `raw`），
做了三项结构性验证：

**① 双向基准校验**（确认分析管线正确）

| 口径 | 结果 |
|---|---|
| 用引擎 `tss` 重建 | **41.11%**（= 现有基线 ✓） |
| 用 `raw + 真 dreq` 重建 | **97.57%**（= 理论天花板） |

97.57% 的人工天花板说明：只要 δ 精准，量化误差只吃掉 2.43%。
56 个百分点的差距全部来自 δ 估计不准。

**② δ 在节内是平滑直线**

以 2013 立春的 41 个样本为例：

```
δ = 9.2416 − 0.0148·x        （x = 距节天数，残差标准差 0.14s）
δ 从 9.5919 (x=−28.6) 单调降到 9.5419 (x=−10.2)
```

但这只是**跨 58 天的极端组**。全样本 280 个「n≥5」组的斜率中位是
**−0.00315 s/天**（P10 −0.00341，P90 −0.00291），与现有表里的
全局 `b = −0.0028` 高度吻合。

**③ 三种拟合粒度都不如现有实现**

| 方案 | 六位全对 | 分位 | 秒位 |
|---|---|---|---|
| 引擎 `tss`（现有） | **41.11%** | 86.7% | 46.3% |
| 组中位 δ（让每样本用自己组的中位数） | 15.20% | 68.9% | 15.5% |
| 组内斜率拟合（min2 / min3 / min5） | 0.03%–0.15% | ~4.9% | ~1.8% |

**连「让每个样本使用自己组的中位数」都远不如现有实现**（15.20% vs 41.11%）。
这反过来证明现有表里的全局斜率 `b = −0.0028` 是有效信息，
比按组自拟合更稳健。

**最终结论**：不是方法不够巧，而是**信息不足**。
δ 的真实值取决于问真内部的节气时刻表，我们的天文算法与之差异
在每节气 0–30 秒之间跳动（δ 表值范围 −29.5 ~ +29.5），
且年际不连续（相邻年份可差 7 秒）。任何平滑/插值/回归都无法从
7651 条稀疏样本里恢复出这张表。

**唯一出路**：每节气补采 ≥100 条密集样本重标 δ（约 15 万请求）。
此前 `dense_fill` 只有 2638 条（每节气约 2 条），反而降到 44%。

## 二、`dyshensha` 顺序 —— 本质不可复刻

### 修正一个此前的错误结论

之前说「49 对神煞全部 50/50 矛盾」——**不准确**。

实测 7651 样本：**39 对可以定序**（矛盾率 < 45%），只有 **10 对真矛盾**。

于是做了一次完整尝试：用 812 条确定约束做拓扑排序，得到 43 个神煞的全局序。

**结果：按此序重排本地结果，逐字一致率仍是 0%。**

### 根因确认

把矛盾按「大运步位（0–11）」分桶统计：

```
亡神 vs 劫煞:
  步0: 亡神在前 202   劫煞在前 201
  步3: 亡神在前 202   劫煞在前 201
  步5: 亡神在前 233   劫煞在前 226
  ...
  步11: 亡神在前 226  劫煞在前 233

将星 vs 桃花:
  步0: 214 : 224    步1: 213 : 202    步2: 188 : 191
  步3: 204 : 229    步4: 191 : 212    ...
```

**每一步都是 200:200 的对称分布**，与柱位无关，与节气无关，与年柱无关。

这不是代码逻辑能产生的模式，是**哈希表 / 集合迭代顺序**的典型特征
（Java `HashMap` 或 Python `set` 的遍历顺序，取决于 hash 值与容量）。

### 补充验证：不是「固定前缀 + 随机尾块」，是纯随机

曾怀疑存在「前几个神煞固定有序、尾段才随机」的结构。对 117,886 个柱位统计
「最长升序前缀长度」：

| 前缀长度 | 占比 |
|---|---|
| 1 | 7.6% |
| 2 | 11.5% |
| 3 | 17.6% |
| **4** | **20.6%**（峰值） |
| 5 | 18.5% |
| 6 | 12.9% |
| 7 | 6.8% |
| 8–12 | 4.6% |

**完全有序的柱：0 / 117,886。**

若存在固定前缀，必然有大量柱匹配到完整长度。这个钟形分布正是
**随机排列**的特征（n 个元素的随机排列，最长升序前缀期望约 4，
分布集中在 3–5）。

「断裂点处」的神煞也均匀分散（天乙贵人 6028、桃花 5034、华盖 4446、
将星 4362…），没有任何聚集，排除了「某几个神煞固定在前」的可能。

**结论**：顺序是纯随机的。要逐字一致只能伪造一个相同分布的随机序，
对信息无任何增益。内容层面已经 **99.6% 一致**，这才是有效信息。

探针：`probe_dyshensha_order.py`（拓扑排序）、`probe_delta_layer.py` 同目录的分位统计

## 三、独家五柱算法 —— 公开接口不存在

### 已查证的三条路径

**1. DEX 静态分析**

```
classes.dex  21,477,364 字节
magic: 6465780a30303500 = "dex\n035\0"（未加密头）
中文串：解出 71 种，全部为乱码（"埒垔"、"蓑琔"、"向唔"…）
熵：接近 8.0（加密载荷）
```

结论：爱加密（ijiami）加固，DEX 是加密壳，静态无法还原。

**2. 关键词搜索**

```
'五柱'     0 次
'wuzhu'    0 次
'fivePillar'  0 次
'wuZhu'    0 次
'第五柱'    0 次
```

在可读的 DEX 区域里**不存在**任何五柱相关字符串。

**3. API 参数穷举**

试了 15 个可能的开关名（`wz` / `five` / `wuzhu` / `n=5` / `col=5` / `pillars=5`
/ `spc` / `full` / `ext` / `mode=2` / `type=2` / `v=2` / `bz5` / `p5` / `extra`）：

**全部无差异**（唯一「变化 1」是 `runtime` 时间戳字段）。

`bz` 字典恒为 9 个键（`0`–`8`），`bz[8]` 是农历字符串，**没有第 10 个键**。

**结论**：「五柱」是 App Store 营销话术，或仅存在于未公开的付费接口。
公开 API 的 27 个字段中没有任何痕迹，无从复刻。
